Guides et senseurs du dépôt Gesta

Inventaire réalisé le 10 novembre 2026 — distinction feedforward / feedback selon la matrice fournie.

Définitions et périmètre

Guide : mécanisme qui donne des consignes avant l'action, à un agent humain ou au programme. Senseur : mécanisme qui observe le code ou son comportement et produit un retour.

L'inventaire couvre les fichiers suivis du dépôt : documentation, configuration, scripts, règles d'exécution et tests. Les dépendances de node_modules/, les sorties de build dist/ et la base binaire locale ne sont pas des mécanismes du projet et sont exclues.

Lecture du statut : exécuté et vérifié signifie qu'une commande a produit le résultat indiqué pendant cette séance. décrit/configuré seulement signifie que le mécanisme existe mais n'a pas été déclenché ici, ou qu'il demande une action humaine.

Fiches vérifiables des mécanismes présents

G1 — Documentation de cadrage

Fichiers : README.md, docs/utilitaire/architecture.md, docs/utilitaire/cdc_gesta_developpement.md, docs/utilitaire/seed.md et backend/API.md.

Demande/impose : décrit l'architecture en couches, les contrats API, les profils, les statuts, le format des erreurs, les commandes et les règles de migration.

Exemple : le jeton est envoyé comme valeur complète de l'en-tête Authorization, sans préfixe Bearer ; une migration doit être un nouveau fichier ordonné.

État : décrit/configuré seulement — consulté pendant l'inventaire, mais ce guide ne s'exécute pas.

G2 — Template de pull request

Fichier : .github/pull_request_template.md.

Demande/impose : renseigner la fonctionnalité, les changements, les vérifications, les tests d'erreur, les droits backend, la documentation API, les migrations et le test navigateur.

Exemple : la checklist exige que npm run check passe sans erreur ni avertissement.

État : décrit/configuré seulement — le fichier a été lu ; aucune PR n'a été créée ou revue pendant cette séance.

G3 — Guides computationnels de qualité

Fichiers : package.json, backend/package.json, frontend/package.json, backend/tsconfig.json, frontend/tsconfig.app.json, backend/.oxlintrc.json et frontend/.oxlintrc.json.

Demande/impose : Node >= 22.14, TypeScript strict, imports cohérents, absence de any explicite, égalité stricte, règles React Hooks et zéro avertissement Oxlint.

Exemple : npm run check enchaîne lint, typecheck, tests et build.

État : exécuté et vérifié — la commande complète a réussi.

G4 — Guides computationnels métier et données

Fichiers : permissions.ts, authenticate.ts, authorize.ts et 001_initial.sql / 002_applications_active_unique.sql.

Demande/impose : les permissions sont évaluées avant l'opération (401/403) et SQLite impose les clés étrangères, les valeurs autorisées, les dates cohérentes et une seule candidature active.

Exemple : canListOffers autorise admin, étudiant ou contact déposant ; l'index unique partiel interdit deux candidatures non retirées pour le même étudiant et la même offre.

État : exécuté et vérifié — couvert par les tests backend lancés dans npm.cmd run check.

S1 — Oxlint

Outil : scripts lint des deux workspaces et leurs fichiers .oxlintrc.json.

Observe : violations de style et de règles TypeScript/React/JavaScript ; les warnings sont refusés par --deny-warnings.

Résultat : aucune erreur ni avertissement signalé.

État : exécuté et vérifié pendant npm.cmd run check.

S2 — TypeScript

Outil : tsc --noEmit backend et tsc -b frontend via les scripts typecheck.

Observe : erreurs de typage, imports, variables inutilisées, branches incomplètes et incohérences de casse selon les options strictes.

Résultat : vérification backend et frontend réussie, sans diagnostic.

État : exécuté et vérifié.

S3 — Tests automatisés

Outils/fichiers : Vitest, Supertest et Testing Library dans backend/tests/ et frontend/tests/.

Observe : comportements API, authentification/permissions, contraintes/migrations SQLite et comportements des pages/hooks React.

Résultat : backend : 10 fichiers, 117 tests réussis ; frontend : 8 fichiers, 49 tests réussis.

État : exécuté et vérifié.

S4 — Builds

Outils : tsc -p tsconfig.build.json et copie des migrations backend ; tsc -b et vite build frontend.

Observe : erreurs de compilation, résolution des modules et production des artefacts frontend/backend.

Résultat : les deux builds ont réussi ; Vite a transformé 60 modules et produit le bundle.

État : exécuté et vérifié.
