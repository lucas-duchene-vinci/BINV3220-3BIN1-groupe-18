Parcours d'affichage des offres

Gesta sépare l'interface React, l'API Express, les règles métier et l'accès SQLite. Cette page retrace le chemin d'un GET /offers jusqu'au tableau visible par l'utilisateur.

Vue d'ensemble

1Composant React

OffersPage demande les données à useOffers.

2Hook

Le hook lance le chargement, gère l'attente, l'erreur et le 401.

3Service frontend

getOffers appelle /api/offers et valide le JSON.

4Route Express

Authentification et autorisation précèdent le contrôleur des offres.

5Service backend

La visibilité dépend du profil de l'utilisateur connecté.

6Repository / SQLite

Une requête SQL joint offres, entreprises, années et périodes.

Parcours détaillé

1. Le composant React déclenche le chargement

La route /offres est rendue par frontend/src/App.tsx lorsque canListOffers(user) l'autorise. Elle transmet à OffersPage l'utilisateur, le jeton et la fonction de déconnexion à utiliser en cas de session invalide.

frontend/src/pages/OffersPage.tsx appelle useOffers(token, onUnauthorized). Selon l'état du hook, la page rend un état de chargement, une erreur, un état vide ou OfferTable. Le tableau affiche le titre, l'entreprise, l'année, la période et le statut; les codes sont traduits par frontend/src/utils/labels.ts.

2. Le hook et le service frontend appellent l'API

frontend/src/hooks/useOffers.ts utilise un AbortController pour annuler une requête lors du démontage ou d'un changement de dépendances. Il appelle frontend/src/services/offers.service.ts. 

GET /api/offers
Authorization: <JWT sans préfixe Bearer>

Le service utilise frontend/src/utils/api.ts pour vérifier le statut HTTP et frontend/src/utils/guards.ts pour valider la structure de la réponse avant de la remettre au hook. frontend/src/vite.config.ts réécrit ensuite le préfixe /api et transmet la requête au backend sur le port 3000.

3. L'API authentifie et autorise

backend/src/app.ts branche la route /offers derrière authenticate. Le middleware backend/src/middlewares/authenticate.ts vérifie le jeton et recharge l'utilisateur, ses rôles et ses entreprises depuis la base. L'autorisation est ensuite appliquée par backend/src/services/permissions.ts via canListOffers.

Dans backend/src/controllers/offers.controller.ts, le contrôleur récupère l'utilisateur courant puis appelle offersService.listOffers(user). Les objets métier sont enfin convertis en DTO de réponse par toOfferDto.

4. Le service applique la visibilité métier

backend/src/services/offers.service.ts transforme le profil en filtre pour le repository :

  • administrateur : toutes les offres;
  • étudiant : uniquement les offres PUBLISHED;
  • contact déposant : les offres dont il est le déposant;
  • contact sans droit de consultation : erreur 403 FORBIDDEN.

Cette couche ne connaît ni Request ni Response : elle porte uniquement les règles métier et délègue la lecture au repository.

5. Le repository lit SQLite

backend/src/repositories/offers.repository.ts prépare une requête SQL paramétrée. Elle lit offers et joint companies, academic_years et periods. Les filtres de statut et de déposant sont facultatifs, puis le résultat est trié par année académique décroissante et date de création décroissante. 

offers
  ├─ company_id       → companies.short_name
  ├─ academic_year_id → academic_years.label
  └─ period_id        → periods.code

La connexion est créée par backend/src/db/database.ts. Le schéma et les contraintes sont définis dans backend/src/db/migrations/001_initial.sql. Le repository renvoie des lignes DBO; backend/src/mappers/offer.mapper.ts les convertit en objet métier puis en DTO, qui remonte la chaîne jusqu'à OfferTable.

Ajout d'un filtre par période

La période existe déjà dans le modèle et dans la requête SQL. L'ajout consiste donc principalement à faire circuler un critère de recherche de l'interface vers le repository, sans modifier le schéma SQLite.
