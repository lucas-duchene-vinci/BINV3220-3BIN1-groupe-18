Parcours d'affichage des offres

De la page React à la requête SQL, ce document retrace le chemin d'une liste d'offres dans Gesta et repère les fichiers à faire évoluer pour ajouter un filtre par période.

Architecture en une phrase

Gesta est un monorepo npm composé d'un frontend React/Vite et d'un backend Express/TypeScript. Le frontend appelle /api/offers; le proxy Vite retire /api et transmet la requête à l'API. Le backend applique l'authentification et les règles de visibilité, puis le repository interroge SQLite avec des jointures explicites.

Parcours de lecture, étape par étape

01 · Route React

frontend/src/App.tsx

Après authentification, App autorise la route /offres lorsque canListOffers(user) est vrai, puis rend OffersPage avec le jeton et le callback de déconnexion.

02 · Page

frontend/src/pages/OffersPage.tsx

La page appelle useOffers(token, onUnauthorized). Elle choisit l'état de chargement, d'erreur, vide ou le tableau de résultats.

03 · Hook

frontend/src/hooks/useOffers.ts

Un effet déclenche le chargement, annule la requête lors du démontage, stocke les offres et traite les erreurs 401 via onUnauthorized.

04 · Service HTTP

frontend/src/services/offers.service.ts

getOffers envoie GET /api/offers avec le jeton brut dans Authorization. readJson vérifie le statut et le type de la réponse.

05 · Proxy et API

frontend/vite.config.ts

Vite redirige /api/offers vers le backend et enlève le préfixe. L'API reçoit donc GET /offers.

06 · Contrôleur

backend/src/controllers/offers.controller.ts

Le middleware authenticate a déjà chargé l'utilisateur. authorize(canListOffers) refuse les profils non autorisés, puis le contrôleur appelle le service et convertit chaque résultat en DTO.

07 · Règle métier

backend/src/services/offers.service.ts

visibilityFilter produit le filtre serveur selon le profil: toutes les offres pour l'administrateur, les offres publiées pour l'étudiant, et les offres déposées par le contact déposant.

08 · SQL et base

backend/src/repositories/offers.repository.ts

Le repository joint offers, companies, academic_years et periods, applique les filtres optionnels, puis trie par année académique et date de création.

Retour des données vers l'écran

SQLite → DBO La requête renvoie notamment period_code, academic_year_label et company_short_name dans OfferDbo.
DBO → domaine backend/src/mappers/offer.mapper.ts transforme les noms SQL en propriétés métier comme period et academicYear.
Domaine → DTO Le même mapper expose uniquement les champs de liste attendus par l'interface: titre, entreprise, année, période et statut.
JSON → modèle React frontend/src/utils/guards.ts valide la forme de la réponse; le hook met à jour son état.
Modèle → affichage frontend/src/components/OfferTable.tsx affiche academicYear, traduit period avec PERIOD_LABELS, puis traduit et colore le statut avec StatusBadge.

Fichiers concernés par un filtre par période

Le code de période existe déjà: P1, P2 et OTHER sont stockés dans la table periods et renvoyés dans chaque DTO. L'évolution consiste donc à faire circuler un critère de filtrage, par exemple period=P1, de l'interface jusqu'au repository.

Fichier Évolution attendue
frontend/src/pages/OffersPage.tsx Ajouter l'état et le contrôle de sélection de la période, puis passer la valeur au hook.
frontend/src/hooks/useOffers.ts Accepter la période comme dépendance de l'effet afin de relancer la liste quand le choix change.
frontend/src/services/offers.service.ts Construire le paramètre de requête, par exemple ?period=P1, en conservant l'annulation et le jeton.
frontend/src/models/offer.ts Réutiliser PeriodCode; éventuellement définir un type de filtre si l'UI en a besoin. Aucun nouveau code de période n'est nécessaire.
backend/src/controllers/offers.controller.ts Lire et valider le paramètre de requête: valeur unique, code autorisé et réponse 400 INVALID_QUERY en cas invalide.
backend/src/services/offers.service.ts Fusionner le filtre de période avec le filtre de visibilité sans permettre au client de contourner les droits.
backend/src/repositories/offers.repository.ts Ajouter periodCode à OfferFilter et à la clause SQL, probablement sur p.code.
backend/API.md Documenter le paramètre, les valeurs admises et les erreurs de validation.
backend/tests/offers.test.ts Tester chaque période, la valeur absente, la valeur invalide et la combinaison avec les règles de visibilité.
frontend/tests/OffersPage.test.tsx Tester le contrôle, la nouvelle requête et le rafraîchissement de la liste après changement de période.
Base de données: aucune migration n'est normalement requise pour ce filtre, car offers.period_id référence déjà periods.code via la jointure existante. Une modification du schéma ne serait justifiée que si le besoin introduisait de nouvelles périodes ou une nouvelle relation.
